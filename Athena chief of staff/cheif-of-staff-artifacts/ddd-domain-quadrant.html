Domain Map — AI Chief of Staff POC

Where to build carefully, where to build simply, and where not to build at all.

Core

The reason this system exists. Nobody else solves it for this company. Worth custom-building and investing your best effort in.

Supporting

Needed to make the core work, specific to how this org operates, but not what makes the system valuable on its own. Build it, but keep it thin.

Generic

Solved the same way everywhere. Buy it, reuse an existing tool or API, or use a built-in feature. Never worth custom engineering.

SubdomainCategoryWhat it actually is
1 Cross-department signal ranking Core Comparing unlike signals (a shipping delay vs. a budget dip) and deciding which one most threatens vision or revenue today. This is the whole point of the system.
2 Policy/vision-grounded reasoning Core Checking every recommendation against this company's own stated priorities, so advice isn't generic — it's specific to what leadership actually said matters.
3 Institutional memory (deferred — Phase 2) Core Recognizing "this looks like what happened in March." Real long-term differentiator, but the POC doesn't need it to prove the concept.
4 Persona-based visibility Supporting Making sure the Product Owner sees only their lane while the CEO sees everything. Necessary and org-specific, not the differentiator.
5 Approval workflow Supporting The "recommend, never act" gate — plan, review, approve. Critical for trust, but a well-worn workflow pattern, not a novel one.
6 Persona-tailored briefing Supporting Same underlying insight, written differently for a CEO vs. a Product Owner. A presentation layer on top of the real work.
7 Department connectors (GoodDay, Outlook) Generic Pulling raw data out of existing tools. Fiddly to wire up (auth, pagination, rate limits) but zero competitive value — every company with these tools faces the same plumbing.
8 Audit & compliance logging Generic Recording who saw what and what was approved. A completely solved problem — use an existing logging pattern, don't design one.

What this means for where POC effort actually goes

Build carefully (2 items)

  • Cross-department ranking logic
  • Policy/vision-grounded reasoning

This is where nearly all the real engineering time should go — it's the only part that makes this a "chief of staff" and not a dashboard.

Build thin (3 items)

  • Visibility scoping (2 personas only)
  • Approval workflow
  • Persona-tailored briefing

Keep these simple on purpose. Over-engineering here just steals time from the two items that actually matter.

Buy or reuse (2 items)

  • GoodDay / Outlook connectors
  • Audit logging

Use the existing APIs directly. Don't write a custom integration framework for a POC — that effort has no payoff here.

The one thing worth remembering: if the POC timeline gets tight, the two Core items are the only ones that can't be cut, mocked, or simplified without losing the actual point of the system. Everything else can flex.
